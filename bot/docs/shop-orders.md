# Durable shop purchases

Apply `20261110193956_bot_reliable_role_purchases.sql` before starting this bot version. Register the returned shop handler's `cleanup()` with the client lifecycle. Orders recover every 15 seconds while that client owns the guild; overlapping clients compete for an atomic 90-second lease, renewed every 30 seconds.

`/buy` checks role existence, existing membership, Manage Roles and bot hierarchy before asking the database to reserve payment. One Discord interaction creates one immutable receipt. Its wallet debit, stock reservation, ledger entry and pending order commit together. Concurrent stock changes and failed ledger writes cannot leave a partial purchase. A new interaction cannot reserve the same role again while an earlier purchase is unresolved.

Role delivery uses Discord's idempotent single-role PUT. Success is recorded only after Discord confirms the PUT, or a fresh member fetch confirms the role from an interrupted earlier attempt. Delivery acknowledgement errors leave the order leased; restart recovery checks Discord instead of refunding a successful role. Non-role products keep the existing purchase-record behavior and complete within the database transaction.

Known permanent failures refund the wallet, increment the current stock, write the refund ledger and finish the order in one transaction, at most once. Transient failures retry at most five times. An ambiguous network outcome is never automatically refunded: a late request could still have granted the role. After bounded recovery fails to establish the outcome, the order becomes `manual_review`. The command and the dashboard explain that staff must check Discord and the order before arranging another delivery or refund. This state retains the charged funds and stock reservation; it is deliberately different from a confirmed failure and refund.

`bot_shop_orders` is the authoritative audit record, including immutable item name and paid price. It survives deletion of a shop listing. `economy_purchases` remains the compatible list of confirmed purchases when the listing still exists. The dashboard's order section filters unresolved orders by default and provides exact counts and pagination, so older unresolved purchases remain reachable. Administrators may read their guild's orders; only service-role code can change order state or call the purchase RPCs.

Run `node --import ./tests/offline-env.mjs --test tests/shop-orders.node.mjs` for real SQL/handler failure, refund, permission, restart, ambiguity and RLS tests. For connection contention, create a fresh isolated database ending `_test` and set `SHOP_TEST_DATABASE_NAME` plus a JSON `SHOP_TEST_PSQL` argv array; then run `node --test tests/shop-orders-postgres.integration.mjs`. Never load those fixtures into production.
