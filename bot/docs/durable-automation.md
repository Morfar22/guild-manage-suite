# Workflow and temporary-moderation recovery

Apply `20261110193958_bot_durable_automation.sql` before deploying these handlers. It adds service-role-only RPCs, backend cursor/job tables, temporary moderation leases, and a dedupe key on operational notifications. Existing guild policies remain in place; the new job table is readable only by the appropriate guild administrators/platform staff, and browser clients cannot mutate worker state.

Temporary unban/quarantine-role removal uses a 90-second renewable lease and at most five attempts. An old `executing` row without a lease is recoverable. Stale workers cannot acknowledge a replacement lease. A member who already left, or a user who is already unbanned, already satisfies the requested final state. Permission/invalid-target errors remain failed and visible rather than being marked executed.

Database-originated ticket/error/raid triggers are atomically inserted into an outbox together with a persistent per-guild scan cursor. A failed SQL transaction advances neither the cursor nor its jobs. Event/workflow uniqueness makes repeated scans and competing processes safe; it also avoids the REST API's default row limit. Existing guild cursors start at migration time to avoid replaying historical events. A five-minute overlap covers ordinary late commits; transactions that deliberately backdate events farther behind an already-advanced cursor are outside this polling guarantee.

Discord member/message events are first written to a private local spool, then enqueued through an idempotent RPC. Keep `/bot/.state` (or `BOT_STATE_DIR`) across deployments and backups. Files/directories use modes 0600/0700, writes use fsync + atomic rename, and files are removed only after confirmed enqueue. A spool holds at most 10,000 events and drains up to 100 per pass. Capacity/disk errors are logged; an event that could not be durably accepted cannot be promised for recovery. Discord gateway events that never reached this process also cannot be reconstructed from this spool.

Corrupt or structurally invalid spool files are retained with an `.invalid` suffix for inspection, and do not block healthy entries. A malformed workflow action configuration produces a visibly failed job rather than poisoning ingestion for every other workflow. Operational execution/acknowledgement failures are logged with the internal guild UUID, including manual-review outcomes discovered during recovery.

Each workflow snapshots its actions and checkpoints them separately. Completed steps are not restarted. Database alerts/cases and their checkpoint commit together. Discord role changes set an idempotent final state. Message requests use deterministic nonces; an ambiguous send or an expired lease while a send was in flight stops for manual review, because Discord and PostgreSQL cannot commit together. Execution history records `partial` if earlier steps completed, and never records full success before all steps are acknowledged. Disabling a workflow skips queued work that has not been claimed yet.

Health/SLA scans run only for guilds owned by that bot client. A database advisory lock and unique active dedupe key serialize competing scanners; older matching notifications are adopted without deleting history. Resolving an incident allows a later incident. An SLA escalation is marked only after its alert is acknowledged; an update failure retries against the same alert.

Validation: `node --import ./tests/offline-env.mjs --test tests/durable-automation.node.mjs`. For real connection contention, use a fresh isolated `*_test` database and the documented `AUTOMATION_TEST_PSQL` argv array in `tests/automation-postgres.integration.mjs`. Never load the fixture into production.
